1. PURPOSE AND THESIS
================================================================================

Squadron Ops is a naval aviation operations platform intended to replace or
outperform legacy squadron tools (OOMA for maintenance, SHARP for training/
readiness) with a modern, integrated web application.

The thesis: one builder can produce a working end-to-end artifact that a Naval
Aviator, maintainer, or program manager recognizes as credible in their domain.
The demo prioritizes believable data, visible cascades (flight → currency →
readiness → maintenance), and polished UX over production hardening.

Target audience for the demo is intentionally broad (squadron CO, SDO, maint
control, TYCOM, NAVAIR PM, investors). The roadmap assumes the highest-
knowledge viewer in the room.

4. ARCHITECTURE
================================================================================

Three-layer backend (invariant — do not break):
  SQLAlchemy models  →  Pydantic schemas  →  FastAPI route handlers

Business logic lives in backend/app/services/, not in route handlers.

Frontend pattern:
  Pages in frontend/src/pages/
  Reusable components in frontend/src/components/
  API client and types in frontend/src/lib/api.ts
  TanStack Query with ~30s stale time

Status color convention:
  Green = good (FMC, current currency)
  Yellow = warning (PMC, expiring, stamped vs computed drift)
  Red = action needed (NMC*, expired, DOWNING discrepancies)

Timestamps: stored UTC, displayed in local time on frontend.

Per-crewmember flight hours live on FlightLog, not sortie-level aggregates.

6. DATA MODEL (DATABASE ENTITIES)
================================================================================

Core operations
  Person              Squadron members (pilots, aircrew, staff roles)
  Aircraft            MH-60S airframes (BuNo, side number, hours, stamped status)
  Sortie              Scheduled or completed flight events
  FlightLog           Per-crewmember sortie participation and hours
  SortieLeg           Multi-leg sortie support
  SortieTaskCredit    CBR task grades per crewmember per sortie
  SortieTmrCode       TMR code hours attached to sorties
  TmrCode             TMR code catalog

Readiness and training
  Qualification       Non-perishable quals (HAC, H2P, NVG, FCP, NSI, INSTR, etc.)
  Currency            Perishable currencies per person
  CurrencyType        Wing Table B-2 catalog (table-driven)
  CurrencyApplicability  Who each currency type applies to
  SyllabusEvent       SWTP event definitions (COMHELSEACOMBATWING 3502.8 codes)
  Gradecard           Training gradesheets
  GradecardLineItem   Syllabus line items on events
  GradecardLineItemResult  Per-student grades on line items
  CbrTaskOption       Capability-based readiness task library (scaffolding)

Maintenance (NAMP / 4790-inspired slice)
  Discrepancy         Open/closed maintenance issues (MAF, JCN, work status)
  InspectionType      Recurring inspection definitions (7 types)
  AircraftInspection  Per-aircraft inspection tracking and due dates

Safety and audit
  SafetyReport        Sortie-linked safety/hazard reports
  InstrumentApproach  Per-crew instrument approaches on flight logs
  AuditLog            HTTP audit trail for consequential API calls

Aircraft status codes
  FMC   Fully Mission Capable
  PMC   Partially Mission Capable
  NMC   Non-Mission Capable
  NMCM  NMC for Maintenance
  NMCS  NMC for Supply

Stamped vs computed status
  Aircraft.status           Line-maintainer stamped value (what brief/OOMA shows)
  computed_status (API)     Derived from open discrepancies + overdue inspections
  Intentional drift in seed (use side numbers, not DB ids):
    614 — stamped FMC, computed PMC (open MAJOR)
    615 — stamped FMC, computed NMCM (DOWNING in work)
    617 — stamped FMC, computed NMCS (DOWNING awaiting parts / AWP)

Maintenance terminology (use in UI — NOT "RTS", which means Ready to Strike):
  QA signoff, QA release, release for flight, safe for flight

7. SEED DATA (python seed.py)
================================================================================

Run from backend/:  python seed.py  (wipes and repopulates)

Typical seeded scale:
  - 8 MH-60S aircraft (side numbers 610–617)
  - ~12 pilots, 8 aircrew, staff (SDO, training officer, maint control, etc.)
  - Wing Table B-2 currency types with ~88% current / ~8% expiring / ~4% expired
  - SWTP syllabus events across PILOT_CORE, PILOT_AMCM, AIRCREW tracks
  - 90+ historical sorties with flight logs, task credits, approaches
  - 12 future scheduled sorties including today's flights for dashboard "Next 24h"
  - One SIM_TOFT sortie (P200 TOFT) for sim-eligible currency demo
  - Discrepancies aligned to aircraft status + 3 drift demo cases (614/615/617)
  - 7 inspection types × 8 aircraft inspection rows
  - Historical gradecards, safety reports, qualifications

Aircraft status mix (stamped):
  5 FMC (3 true + 2 drift at 614/615), 1 PMC (616), 1 FMC with NMCS drift (617)
  ~50% computed FMC after discrepancy logic

12. SORTIE COMPLETION CASCADE (SPINE OF THE APP)
================================================================================

When POST /logging/sorties/{id}/complete runs:

  1. Updates sortie times, completion flag, flight mode
  2. Writes/updates FlightLog rows per crewmember (hours, landings, approaches)
  3. Renews applicable currencies (only advances if event_date >= last_event_date)
  4. Increments aircraft total_airframe_hours
  5. Records SortieTaskCredit grades
  6. Files Discrepancy records if provided
  7. Creates SafetyReport records if provided
  8. Attaches SortieTmrCode hours

Observable demo path:
  Schedule/complete NVG sortie → crew NIGHT_NVD currency extends → aircraft
  hours increment → any filed discrepancy appears on aircraft maintenance page.

================================================================================
13. QA RELEASE WORKFLOW (MAINTENANCE)
================================================================================

Problem: Stamped status (Aircraft.status) can lag computed status when open
discrepancies change but line paperwork has not been updated.

Solution: Maintainer completes work → QA signoff → QA release:
  - Optional: close selected discrepancies with corrective action
  - Validates blockers (open DOWNING, overdue downing inspection, NMC*)
  - Sets aircraft.status = computed_status
  - Clears manual_status_override
  - Appends QA notes to aircraft.notes

UI: Maintenance page drift banner → aircraft maintenance detail → QA Release
card/modal → "Release for Flight" button.
